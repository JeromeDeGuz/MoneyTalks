# Team Retrospective – Iteration 1 (MoneyTalks)

## Getting Started Challenges (What happened early on)
At the beginning of the project, we struggled to start the codebase confidently. This late start became one of the biggest reasons we had to cram near the end, which reduced the time we could spend on polishing and small improvements for Iteration 1.

We felt we started “for real” about 1.5 weeks after Iteration 0 was due. There were a few key reasons:
- We only met as a full group about once a week, which created long gaps and made it harder to stay fully aligned.
- We were not familiar with Android Studio’s folder/package structure, so we were unsure what files should go where and how to begin.
- We also needed time to understand how UI (front-end) elements connect together in Android, which increased anxiety and uncertainty at the start.

However, once we met, clarified responsibilities, and pushed through the early confusion, we regained momentum and got back on track for the deadline.

## What Worked Well
After we got into a steady workflow, the project started to “click” and we developed better team synergy. GitLab helped us stay organized:
- We used issues (especially dev tasks) to split work clearly.
- Each member could see what they owned and what was blocked.
- Tracking tasks made it easier to move from planning to implementation.

## What Could Be Improved
Our biggest improvement area is communication frequency.
Because our schedules do not always align, meeting only once per week was not enough. We need to sacrifice a little more evening/weekend time to meet remotely, touch base more often, and stay aligned on:
- who is doing what,
- what issues are active,
- what is blocked or needs review.

More frequent check-ins would help us start the next iteration with more confidence and reduce last-minute pressure.

## Action Items for Next Iteration (Concrete changes)
- Add 1–2 short remote check-ins per week (15–30 minutes) to reduce long gaps.
- Create a simple “project structure guide” in the docs (where each package/file type should go).
- Start the iteration by building a working skeleton early (basic navigation + stub data), so feature work can begin sooner.
- Use smaller merge requests and merge earlier to avoid last-minute conflicts and rushed testing.
